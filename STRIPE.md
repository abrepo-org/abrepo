# Stripe Notes

These are notes about general Stripe behavior. This is not necessarily
specific to `abrepo`, which is integrated with devise and user
creation; found in [DEVISE-STRIPE.md](./DEVISE-STRIPE.md).


## Install

1. Create an account on Stripe
2. Install 'gem stripe'
3. Set stripe keys: `PUBLISHABLE_KEY, SECRET_KEY, WEBHOOK_KEY`
    * need to create a webhook (externally accessible route) to generate a key.
    * webhooks are locally accessible/tested via the stripe CLI.
4. create config/initializers/stripe.rb:

```
Stripe.api_key = ENV['STRIPE_SECRET_KEY']

```

5. Add ENV['STRIPE_DEFAULT_LOOKUP_KEY'] - references a lookup_key for
   a default Stripe Price object created via dashboard or CLI
6. Make sure price 'nickname' is added - this is text displayed.



Stripe accounts have their own test/prod environments and
keys. Accounts are toggled to "test" by default, and need to manually
be toggled to live.


## Stripe CLI

Used to test a webhook locally; installed in the `Dockerfile` via
apt-get.

You will need to re-authenticate on every `docker-compose` session -
auth will persist only during lifetime of a running container.

To run the stripe cli, run `./docker_run.sh bash`, which `exec`'s into
the running `web` container, and run `stripe login`.

#### Products and Prices

Create a product and prices at the same time. Once prices are created
and there is a subscription, `Price` is locked. Pattern is to create
new prices on change (so old subscriptions don't suddenly have new pricing.)

* Create a `Product`: "ABrepo Basic"
* Create `Price` instances associated with that Product:
    * Annual Subscription
    * Basic Subscription
* Make sure to setup Customer Portal (see below) for
  `/users/:id/edit/` to manage account.

When moving Product / Price to live mode; `lookup_key` is **not**
transferred, and need to be updated with CLI with keys in staging /
prod environment.


#### Checkout

Purchase Flow:

1. render `checkout#index` -> user buys -> POST /create-checkout-session (`checkout#createSession`)

2. `checkout#createSession` -> builds stripe configuration elements
   and returns to client, then Stripe "takes over" the transaction

3. User enters info on stripe page, eventually buys or cancels and
   returns to your app

4. cancel  -> render cancel page

5. success -> render success page & /webhook


`checkout_controller.rb`:

* `index`: initial pricing page. requires `price_id`
    * `price_id`: can set in stripe dash/api. Hardcoded id, or
      referenced with a `lookup_key` (see below.)
    * `Stripe::Price` is an API request, so might be valuable to
      cache.
* `createSession`: creates Stripe session config object, returns to
  client for handoff to Stripe
* `cancel`: user cancels purchase, renders cancel page
* `success`: post purchase completion, renders success page

##### `lookup_key`:


* https://stripe.com/docs/billing/prices-guide#managing-prices
* Prices can have a lookup_key. The key can only be created/managed
  via CLIA/API.
* If want a new price reflected while using same lookup key, when
  creating or updating the price add param `transfer_lookup_key=true`

NB: Once a price is subscribed, the actual price is locked and can't
be changed (id -> price is set) - you need to create a new price
object (e.g. imagine current users suddenly having their subscription
changed.), and then transfer lookup key to keep application in sync.

* This param doesn't transfer from test - needs to be reset via Stripe
  CLI. Make sure to look at --live examples below, using a
  permissioned `api_key`

#### Stripe CLI Examples

* https://stripe.com/docs/billing/prices-guide
* https://stripe.com/docs/billing/prices-guide#managing-prices

```
# see all resources
stripe resources list

# create product and make sure to save id
stripe products create \
  --name="ABRepo Basic" \
  --description="ABRepo Search Subscription"

# list products (get prod id)
stripe products list


#
# PRICE
#

# create prices
# NB: use of `-d` as its a nested obj
# "unit amount" is in cents -> example below is $10.00 price.
stripe prices create \
  -d product={{PRODUCT_ID}} \
  -d unit_amount=1000 \
  -d currency=usd \
  -d recurring[interval]=month
  -d lookup key="basic-monthly"

# new price, taking over lookup_key
stripe prices create \
  -d product={{PRODUCT_ID}} \
  -d unit_amount=1000 \
  -d currency=usd \
  -d recurring[interval]=month
  -d lookup key="basic-monthly"
  -d transfer_lookup_key=true

# list prices
stripe prices list

# list by lookup (data return is array)
stripe prices list -d lookup_keys[]="basic-monthly"

# update and transfer lookup key back
stripe prices update <price_id> \
    -d lookup_key="basic-monthly" \
    -d transfer_lookup_key=true

# LIVE MODE
# required params
# --live -p=abrepo --api-key=<key>
#
# API KEY needs to have core WRITE permissions enabled to make changes
# go to api key -> edit, set core to WRITE.
# might have to try this a few times. Should look active (not disabled)
#
# should NOT need to login for live
# stripe login will result in 'default' project with test keys that don't match
# project.

# get a price in LIVE mode (default is test)
# use the --live param
stripe get <price_id123> --live -p=abrepo

# update lookup_key that don't follow when transferring from test mode
stripe prices update <price_id> \
    -d lookup_key="basic-monthly" \
    -d transfer_lookup_key=true \
    --live
    --api-key=<id>


```

##### Stripe Fixtures

Currently saved in: `test/fixtures/files/<file.json>`

Stripe fixtures execute custom fixtures, best modified on the `stripe
trigger` webhook request examples. To customize requests, download the
corresponding
[base template](https://github.com/stripe/stripe-cli/blob/master/triggers/) associated
with the eventm and populate accordingly.


```
# executing checkout.session.completed trigger, but added 'client_reference_id'
stripe fixtures test/fixtures/files/checkout.session.completed.json

# test charge.failed
stripe fixtures test/fixtures/files/charge.failed.json

```

The rails webhook will receive your modified fixture event.

#### Manage Subscriptions - Customer Portal:

For paid users, on users/edit, display button sending user to management portal.

On button click, POST request that looks up stripe_customer_id,
requests from stripe the valid management url to redirect user. User
only sees a fetch and a url response (auth, customer_id all handled in
server.)

Need to setup _Customer Portal_ within Stripe dashboard before portal
is available:

* Settings -> Billing -> Customer Portal

Current Enabled (MONTHLY ONLY):
* Invoice History
* Billing Information (email, billing)
* Payment Methods: enabled
* Cancel Subscriptions: allow, cancel at end of billing period
* Update Subscriptions:
    * Allow switch to different pricing plan
    * Prorate subscription updates (Issue invoice immediately)

Make sure to add only Monthly Product - whole point of annual plan is
to pay upfront.

Requires URLs for:

* Terms of Service (https://<host>/privacy-policy)
* Privacy Policy (https://<host>/terms-of-service)

Verify in Prod.

Portal can be setup to allow:

* Payment Changes
* Cancel Subscription - immediately vs end-of-period (maybe disable for now)
* Switch Plans




## Frontend JS - Checkout Client

### checkout#index

`content_for(:footer)` block wraps stripe.js to load in `<footer>` and
contains subscription code. `priceId` is the main input, loaded in the
`checkout#index` controller.

1. onClick: create an internal request POST request to
   `/create-checkout-session` containing user's price selection.

2. `/create-checkout-session` returns a configured checkout session
   object (success, cancel state, types, configured payment type,
   etc.)

3. Client JS receives session and redirects to Stripe hosts for checkout.

4. Redirect to Success / Cancel page (no stripe needed on these pages.)
